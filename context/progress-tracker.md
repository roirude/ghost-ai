## Architecture Decisions

- `app/globals.css` previously had no theme at all (`@import "tailwindcss";` only). The dark theme token table in `context/ui-context.md` was not yet implemented in CSS, so it was added here as part of this unit rather than deferred, since shadcn components need real tokens to render dark-first and the spec's own done-check ("No default light styling appears") depends on it.
- The installed `shadcn` CLI (v4.21.0) has moved to a new default architecture (`base-nova`/`radix-nova` presets, `@base-ui/react` or a bundled `cn` npm package, `@tabler/icons-react` as default icon lib) that no longer matches classic shadcn/ui conventions or this project's spec (which calls for a locally-defined `cn()` and `lucide-react`). Rather than accept CLI defaults, `components.json` and all `components/ui/*` files were hand-authored using classic Radix-primitive shadcn/ui source, restyled to this project's token names. Future `shadcn add` CLI usage should be checked against this convention before trusting its output.
- Next.js 16 deprecated and renamed the `middleware.ts` file convention to `proxy.ts` (function renamed `middleware` → `proxy`); `context/feature-specs/03-auth.md` calling for `proxy.ts` over `middleware.ts` is this rename, not a project-specific choice — confirmed against `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`.
- `@clerk/nextjs@7.9.2`'s `createRouteMatcher` is marked `@deprecated` in favor of resource-based auth checks (auth calls inside each page/route instead of centralized path matching), per its own type doc comment. Used it anyway here because the spec explicitly asks for public-route matching driven by env vars in `proxy.ts`, which is inherently a route-matcher pattern — this is a deliberate spec-driven exception, not an oversight. If Clerk removes `createRouteMatcher` in a future major version, this will need to move to per-route `auth.protect()` calls.
- `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` did not exist in `.env.local` before this unit (only the publishable/secret keys did). Added them rather than hardcoding `/sign-in` and `/sign-up` path strings in `proxy.ts`, since the spec says to define public routes "using the existing sign-in and sign-up env vars" and these are Clerk's own standard variable names (read directly by `@clerk/nextjs`'s internals) rather than app-invented ones.
- `package.json` had `@prisma/client@^7.10.0` / `@prisma/adapter-pg@^7.10.0` already installed, but `prisma` (the CLI/devDependency) was still `^6.19.3` — a CLI/client major-version mismatch that fails schema validation (v7's `prisma-client` generator and config-based datasource are v7-only). Upgraded `prisma` to `^7.10.0` to match, since the spec assumes a working v7 toolchain rather than a mismatched one. Also added `@prisma/extension-accelerate` (not previously listed as "already installed" in the spec) since the spec's Accelerate branch requires it — a bare `@prisma/client` v7 has no `accelerateUrl` support without this extension.
- `prisma/schema.prisma`'s `datasource` block still had `url = env("DATABASE_URL")`, which Prisma 7 rejects (`P1012`) — connection URLs moved to `prisma.config.ts`. Removed `url` from the schema; it was already correctly present in `prisma.config.ts`. Also removed `engine: "classic"` from `prisma.config.ts`, a v6-era `PrismaConfig` field that no longer type-checks in v7.
- `.env` (committed-safe placeholder file) has no real `DATABASE_URL`; the actual value lives in `.env.local` per Next.js convention, which plain `dotenv/config` does not load by default. `prisma.config.ts` now explicitly loads `.env.local` before falling back to `.env`, so `prisma generate`/`migrate` pick up the real database URL.
- The project's `DATABASE_URL` was originally a `prisma+postgres://localhost:...` URL pointing at a local `prisma dev` server. During the `07-wire-editor-home` unit, that local server started failing every query with `PrismaClientKnownRequestError: Using an HTTP connection string is not supported with Prisma Client version 7.10.0 by this version of prisma dev` — the running server process (PID confirmed via `netstat`) had a start time predating the `prisma` CLI's `^6.19.3` → `^7.10.0` upgrade (see the entry above) and was speaking a stale wire protocol; killing it left a stale lock at `%LOCALAPPDATA%\prisma-dev-nodejs\Data\durable-streams\default\server.lock(.lock)` that had to be deleted before a fresh `prisma dev` could bind. Rather than keep depending on a fragile local dev server, `DATABASE_URL` in `.env.local` was switched to a hosted Prisma Postgres pooled connection string (`postgres://...@pooled.db.prisma.io:5432/postgres?sslmode=require`, provided directly by the user) — a plain `postgres://` URL, so `lib/prisma.ts` now routes it through the direct `PrismaPg` adapter branch instead of the Accelerate branch. `npx prisma migrate deploy` applied the existing `20260913150638_init_project_models` migration cleanly against it. Local `prisma dev` is no longer required for this project's day-to-day development; if a future session needs to fall back to it, be aware the stale-lock issue above can recur if the server process is killed without a clean shutdown.
- `lib/prisma.ts`'s cached client is now typed as the Accelerate-extended shape (`ReturnType<typeof createAcceleratedClient>`) rather than a union of both branches — a union made every model method (`.findMany`, `.create`, etc.) uncallable under `strict` because the two branches' overload sets don't unify. The direct-adapter (`PrismaPg`) branch is cast to this shared type; both branches expose the same model-query surface in practice, only extension-internal plumbing (`$on`, etc.) differs.
- `proxy.ts` cannot use a single `auth.protect()` call for both page routes and API routes: `auth.protect()`'s default unauthenticated behavior is an HTTP redirect, which is correct for pages but produces a `307` (not `401`) for `fetch`/API clients. API routes now get their own `auth()` check inside the proxy with a manual `401` JSON response.
- The Prisma `Project` model has no dedicated "room ID"/slug column — just `id` (a `cuid()` by default) and `name`. `07-wire-editor-home.md` requires the project ID and Liveblocks room ID to "stay aligned," so rather than adding a schema column, `POST /api/projects` now accepts an optional client-supplied `id` and uses it verbatim as the Prisma record's id when present (`lib/projects.ts`'s `createProject(ownerId, name, id?)`). The client (`hooks/use-project-actions.ts`) generates that id once per create-dialog session as `slugify(name)-<6-char-random-suffix>`, uses it for both the live `ghost.ai/<id>` preview and the actual `POST` body, so the previewed value and the created project's real id are always identical. No collision-retry logic was added — the random suffix makes collisions negligible and the spec has no requirement calling for retries.
- `lib/slug.ts` exists only to hold `slugify()` separately from `lib/projects.ts`. `lib/projects.ts` imports `lib/prisma.ts` (and transitively `@prisma/client`), which must never end up in client-bundled code; `hooks/use-project-actions.ts` is a `"use client"` hook that needs `slugify()` for the live room-id preview, so it imports from `lib/slug.ts` instead.
