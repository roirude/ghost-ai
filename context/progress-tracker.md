## Notes From This Unit

- `Presence.isThinking` was renamed to `thinking` to match this spec's named shape (`cursor`, `thinking`). It had exactly two references — the type in `liveblocks.config.ts` and `RoomProvider`'s `initialPresence` in `canvas-room.tsx` — and no reader anywhere, so the rename was a two-line change with no behavioural consequence. Nothing writes `thinking` yet; the AI generation unit is its first producer.
- **Cursors are broadcast in canvas coordinates, not screen pixels.** `onMouseMove` runs `screenToFlowPosition` before writing presence, so each peer resolves the point through their own viewport transform and the pointer lands on the same spot of the diagram no matter how they have panned or zoomed. Broadcasting `clientX`/`clientY` would have pinned remote cursors to screen positions that mean nothing on another viewport.
- The companion decision: `CanvasCursors` renders inside React Flow's `ViewportPortal`, which mounts children into the pan/zoom-transformed layer. That is what makes canvas-space coordinates render correctly with zero position syncing — no viewport subscription, no manual transform math. It is also why `<CanvasCursors />` sits *inside* `<ReactFlow>` while `<PresenceAvatars />` sits outside it: the portal has no viewport to attach to otherwise.
- `PresenceAvatars` filters `useOthers` on `other.id !== currentUserId` even though `useOthers` already excludes the local connection. The filter is not redundant — the same Clerk user can have the project open in two tabs, and each tab is a separate Liveblocks connection that appears in the other's `others` list. Without the ID filter that user would see themselves as a collaborator avatar *and* as the Clerk `UserButton`, which is the exact double-render the spec forbids.
- Both presence selectors pass `shallow`. `useOthers` fires on every presence change in the room — which is every cursor move of every peer, up to 60/s — so an unmemoised selector would allocate a fresh array and re-render the avatar stack on each one. `shallow` limits renders to frames where a value actually changed, which for the avatar group means join/leave rather than pointer motion.
- Collaborator avatars are `aria-hidden` + `pointer-events-none` `<div>`s, not buttons: the spec requires display-only, and inert elements also keep the top-right stack from swallowing clicks meant for the canvas beneath it.
- The presence group lives in the *canvas* (`canvas.tsx`), not in `WorkspaceNavbar`. `WorkspaceNavbar` already renders its own `UserButton` and is shared with no other route, but the editor-home navbar (`editor-navbar.tsx`) is a separate component and was not touched — so presence UI cannot leak onto the project-list route. The canvas group renders a second `UserButton` by design: the spec asks for the current user to appear in the canvas group itself, and Clerk's `UserButton` is stateless, so two instances are independent and both work.

- The spec for this unit names tokens that do not exist in this project (`bg-base/95`, `text-primary-text`, `text-muted-text`, `bg-accent`, `text-accent`, `bg-subtle`, `text-accent-text`, `bg-brand-dim`, `bg-elevated`). Per the spec's own "check `globals.css` before adding direct color values" rule, each was translated to the real `@theme inline` name: `bg-bg-surface/95`, `text-copy-primary`, `text-copy-muted`, `bg-accent-ai`/`text-accent-ai`, `bg-bg-subtle`, `text-accent-ai-text`, `bg-accent-dim`, `bg-bg-elevated`. No new colors were introduced.
- **`accent` is a trap token here.** shadcn's `--accent` maps to `--bg-subtle` (a grey surface), *not* to a brand color. A literal `bg-accent` for the active tab and send button would have rendered grey-on-grey. The AI accent is `--accent-ai` (`#6457f9`), exposed as `bg-accent-ai`/`text-accent-ai`, and that is what the sidebar's accent styling uses.
- The active tab uses `bg-accent-ai/15` rather than solid `bg-accent-ai`: the `TabsTrigger` default already sets `data-[state=active]:bg-bg-elevated data-[state=active]:text-copy-primary`, and a solid indigo fill under `text-accent-ai` indigo text is unreadable. A 15% wash keeps the accent legible while still reading as selected.
- Auto-resize resets the textarea to `COMPOSER_MIN_HEIGHT` *before* reading `scrollHeight`. Skipping the reset measures the previous (taller) box, so the composer can grow but never shrink back as text is deleted.
- The floating `<aside>` — position, width, border, `bg-bg-surface/95`, backdrop blur, shadow, and the `translate-x-full` slide — moved verbatim from `workspace-shell.tsx` into `ai-sidebar.tsx`. Open/close state stays in the shell (`isAiSidebarOpen`), passed down as `isOpen`/`onClose`, so the navbar toggle keeps working unchanged.
- Chat state is local `useState` and messages are user-only: there is no assistant reply path yet. `ChatMessage.role` already carries `"assistant"` and the bubble renders it, so the generation unit adds a producer rather than a renderer.

## Architecture Decisions

- `app/globals.css` previously had no theme at all (`@import "tailwindcss";` only). The dark theme token table in `context/ui-context.md` was not yet implemented in CSS, so it was added here as part of this unit rather than deferred, since shadcn components need real tokens to render dark-first and the spec's own done-check ("No default light styling appears") depends on it.
- The installed `shadcn` CLI (v4.21.0) has moved to a new default architecture (`base-nova`/`radix-nova` presets, `@base-ui/react` or a bundled `cn` npm package, `@tabler/icons-react` as default icon lib) that no longer matches classic shadcn/ui conventions or this project's spec (which calls for a locally-defined `cn()` and `lucide-react`). Rather than accept CLI defaults, `components.json` and all `components/ui/*` files were hand-authored using classic Radix-primitive shadcn/ui source, restyled to this project's token names. Future `shadcn add` CLI usage should be checked against this convention before trusting its output.
- Next.js 16 deprecated and renamed the `middleware.ts` file convention to `proxy.ts` (function renamed `middleware` → `proxy`); `context/feature-specs/03-auth.md` calling for `proxy.ts` over `middleware.ts` is this rename, not a project-specific choice — confirmed against `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`.
- `@clerk/nextjs@7.9.2`'s `createRouteMatcher` is marked `@deprecated` in favor of resource-based auth checks (auth calls inside each page/route instead of centralized path matching), per its own type doc comment. Used it anyway here because the spec explicitly asks for public-route matching driven by env vars in `proxy.ts`, which is inherently a route-matcher pattern — this is a deliberate spec-driven exception, not an oversight. If Clerk removes `createRouteMatcher` in a future major version, this will need to move to per-route `auth.protect()` calls.
- `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` did not exist in `.env.local` before this unit (only the publishable/secret keys did). Added them rather than hardcoding `/sign-in` and `/sign-up` path strings in `proxy.ts`, since the spec says to define public routes "using the existing sign-in and sign-up env vars" and these are Clerk's own standard variable names (read directly by `@clerk/nextjs`'s internals) rather than app-invented ones.
- `package.json` had `@prisma/client@^7.10.0` / `@prisma/adapter-pg@^7.10.0` already installed, but `prisma` (the CLI/devDependency) was still `^6.19.3` — a CLI/client major-version mismatch that fails schema validation (v7's `prisma-client` generator and config-based datasource are v7-only). Upgraded `prisma` to `^7.10.0` to match, since the spec assumes a working v7 toolchain rather than a mismatched one. Also added `@prisma/extension-accelerate` (not previously listed as "already installed" in the spec) since the spec's Accelerate branch requires it — a bare `@prisma/client` v7 has no `accelerateUrl` support without this extension.

  `lib/canvas-storage.ts` is the new storage module. Blobs are written at the stable key `canvas/{projectId}.json` — the path the architecture context already specifies — with `access: "private"`, `addRandomSuffix: false` and `allowOverwrite: true`. Both flags are load-bearing together: without `addRandomSuffix: false` every autosave would mint a new key, so a project editing session would accumulate one orphaned blob per debounce window, and with a fixed key the overwrite must be opted into or the second save 409s. **The store attached to this project is a private store, and a private store rejects `access: "public"` outright** — the first runtime attempt failed with `Vercel Blob: Cannot use public access on a private store` on every autosave (HTTP 500 per edit), which the initial implementation had not caught because the build and lint gates never touch the store. Private is also the correct level on the merits: a canvas belongs to its project's members, and a public blob URL would be readable by anyone holding the link, bypassing the access checks on the route entirely. The consequence is that **reads cannot use a bare `fetch`** — the stored URL carries no credentials against a private store — so `loadCanvasSnapshot` goes through the SDK's `get(url, { access: "private", useCache: false })` and buffers `result.stream` through `new Response(...).json()`. `useCache: false` serves the purpose the previous `cache: "no-store"` did: the key is reused on every save, so a CDN-cached copy would hand back a stale canvas. `get` returns `null` for a missing blob, which folds into the existing "treat a missing snapshot as an empty canvas" branch with no extra handling. `parseCanvasSnapshot()` validates only the envelope (`nodes`/`edges` must be arrays): the elements are React Flow node/edge objects whose full shape belongs to the canvas renderer, and re-validating them at the API boundary would duplicate that schema in a second place and drift from it. The snapshot carries `version: 1` so a future shape change is recognisable on read rather than silently misparsed. A blob URL that no longer resolves returns `null` rather than throwing — the editor's only sensible response to "saved canvas missing" is the same as to "never saved", namely an empty canvas.

  `app/api/projects/[projectId]/canvas/route.ts` holds `GET` and `PUT`. Both gate on **project access** (`findProjectWithAccess` + `hasProjectAccess` from `lib/project-access.ts`), not ownership, unlike the rename/delete routes on the sibling `[projectId]/route.ts` — collaborators edit the canvas, so an owner-only save boundary would have made every collaborator's autosave 403 while their edits still synced through Liveblocks, silently losing their work on the next owner save. This is the same access rule the Liveblocks auth route issues room tokens under, which keeps "can join the room" and "can persist the room" from diverging.

  `hooks/use-canvas-autosave.ts` debounces at **1500ms** of stillness. It compares the serialised payload against a `savedPayloadRef` before scheduling, so a re-render that did not change the graph — a selection change, a peer's cursor moving — never queues an upload; without that guard the hook would save on every presence frame. The first pass after `enabled` flips adopts the current payload as the baseline rather than saving, so loading a canvas does not immediately re-upload what was just read back. The effect's cleanup both `clearTimeout`s and sets an `ignore` flag, so an edit inside the debounce window cancels the pending save and a response arriving after unmount cannot set state.

  `hooks/use-canvas-load.ts` implements the spec's central invariant: **an occupied room is never restored into.** The room is the source of truth while anyone is connected, so replaying a snapshot into live collaborative state would overwrite whatever peers are working on. The room-empty check is made twice — once before the fetch and again after it resolves — because a peer can join and start drawing, or import a template, while the request is in flight; only the second check catches that race. The hook returns `isLoaded`, which gates autosave, and that ordering is what stops the empty pre-load canvas from being written over a real saved one. A `hasRunRef` makes the effect run exactly once per mount regardless of graph changes, and the room contents are read through a ref synced in its own effect rather than during render — writing `ref.current` in the render body is a `react-hooks/refs` lint error, and effects in the same component run in declaration order, so the sync effect populates the ref before the load effect reads it on mount. The restore is written through the `onNodesChange`/`onEdgesChange` handlers `useLiveblocksFlow` owns, so it is an ordinary Storage write that syncs to peers and lands in the room's undo history — the same path `importTemplate` already used.

  `components/editor/save-status-button.tsx` is the navbar indicator. It is deliberately a *disabled* button: the canvas saves itself, so there is nothing to click, and rendering it as a button keeps visual parity with the rest of the navbar. `aria-live="polite"` announces transitions, `Loader2` spins while saving, and the error state uses `text-state-error` / success `text-state-success` (the real token names — `accent-danger-text` does not exist in `globals.css`). Status travels from inside the room to the navbar via an `onSaveStatusChange` prop threaded through `CanvasRoom` into `WorkspaceShell` state, the same boundary-crossing pattern `onImportReady` established, because the navbar renders above `RoomProvider` and cannot call Liveblocks hooks. Passing `setSaveStatus` directly is safe — a `useState` setter is referentially stable, so the reporting effect cannot loop. `CanvasImportHandle` was widened into a `CanvasProps` interface carrying `projectId` and `onSaveStatusChange`; `CanvasImportHandle` is still exported and still describes the import handoff.

  Verified: `npm run build` passes with `/api/projects/[projectId]/canvas` registered as a dynamic route, `npx tsc --noEmit` is clean, and `npm run lint` is clean apart from the pre-existing `no-img-element` warning in `share-dialog.tsx`. The blob layer **was** exercised against the real store this time, via a throwaway script run under the project's `.env.local` (removed afterward; `git status` confirms no leftover): a private `put` at the canvas pathname succeeded and returned a `*.private.blob.vercel-storage.com` URL, `get` by that URL round-tripped the exact payload, a second `put` to the same pathname read back the **new** content (confirming `useCache: false` defeats the CDN and that overwrite-at-a-stable-key works), and `get` on a nonexistent pathname returned `null`. This is the check that should have run before the first hand-off — the public/private mismatch was only reachable at runtime.

  Still not verified at runtime: the editor-side behaviour — the empty-room-only restore, the debounce coalescing, and the collaborator-access save path — which needs real Clerk credentials and a live Liveblocks room, the same limitation noted in `07`-`09`, `13`-`15`. **Lesson for future storage units: a green build and lint say nothing about whether the configured store accepts the write.** Exercise the external service directly before reporting a storage feature complete.
